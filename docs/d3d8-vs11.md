# D3D8 programmable vertex shader 1.1

Status: enabled in signed XPDriver 1.0.0.209 and retained through 1.0.0.215.
`VertexShaderVersion` is 1.1 and `MaxVertexShaderConst` is 96 after the guest
translator, transport-43 host execution, stock-System32 D3D8 rendering, exact
host capture, and broad fixed-function regression gates passed together. The
remaining shader-specific lifecycle matrix is recorded below. This work does
not enable the D3D9 DDI v4 path.

## Scope and invariants

The target is the complete Direct3D 8 `vs_1_1` surface exposed through the
stock XP Direct3D runtime. Applications continue to create shaders with
`D3DNTDP2OP_CREATEVERTEXSHADER`, bind them with `SETVERTEXSHADER`, and update
constants with `SETVERTEXSHADERCONST`. The XP display driver translates valid
bytecode to an ARB vertex program and transports it to the existing host GL
session. Replacement Direct3D DLLs are not part of the design.

The capability is governed by these invariants:

- all required `vs_1_1` instructions and legal register forms translate;
- malformed, truncated, over-budget, and semantically invalid streams fail
  without an out-of-bounds read or partial live object;
- declarations, declaration constants, runtime constants, state blocks,
  reset, delete, and process teardown have deterministic ownership;
- relative addressing rounds like D3D and returns zero for constant indices
  outside `c0..c95`;
- D3D clip-space `z` in `[0,w]` is converted to GL clip-space `[-w,w]`;
- the host has enough temporary registers for the exact translation;
- programmable user clip planes remain exact even though non-position-
  invariant ARB vertex programs disable OpenGL's fixed user clipping;
- software vertex processing and fixed-function hardware T&L regressions are
  unchanged; and
- exact host tests and a signed fresh-install real-XP acceptance both pass.

The `.209` package advertises the implemented 1.1/96-constant contract. The
translator and packet validators continue to fail closed for unsupported or
invalid input; a future shader model or opcode must not be advertised until
its complete path has equivalent coverage.

## Stock D3D8 command contract

The WDK D3D8 DP2 stream defines these commands:

| Command | Payload |
| --- | --- |
| `CREATEVERTEXSHADER` (45) | handle, declaration byte count, function byte count, declaration tokens, then function tokens |
| `DELETEVERTEXSHADER` (46) | handle |
| `SETVERTEXSHADER` (47) | shader handle, or an FVF value for the existing fixed-function path |
| `SETVERTEXSHADERCONST` (48) | first register, vector count, then `count * float4` values |

A programmable shader object owns its declaration, translated host program,
and declaration constants. Context runtime constants are separate state.
Every `SETVERTEXSHADER` bind reloads the declaration constants into the
context; later runtime/state-block writes remain effective only until the next
bind of that shader. Reset and process teardown must delete host programs
exactly once.

## Declaration grammar

The declaration is a bounded DWORD token array ending in `0xffffffff`.
Supported tokens for the first capability milestone are NOP, stream selector,
stream load/skip, constant-memory load, and END. Tessellator and extension
tokens are rejected while the corresponding patch/tessellation capabilities
remain zero.

Only stream zero is advertised by the current driver, so declarations naming
another stream are rejected. Loads map to `v0..v15`; a register may not be
loaded twice and the computed byte offset and stride must not overflow.

| Type | Bytes | Expanded input |
| --- | ---: | --- |
| `FLOAT1` | 4 | `(x, 0, 0, 1)` |
| `FLOAT2` | 8 | `(x, y, 0, 1)` |
| `FLOAT3` | 12 | `(x, y, z, 1)` |
| `FLOAT4` | 16 | `(x, y, z, w)` |
| `D3DCOLOR` | 4 | normalized ARGB bytes as `(R, G, B, A)` |
| `UBYTE4` | 4 | unnormalized `(x, y, z, w)` |
| `SHORT2` | 4 | `(x, y, 0, 1)` |
| `SHORT4` | 8 | `(x, y, z, w)` |

`D3DVSD_CONST(address,count)` carries `count * 4` following DWORDs and may
initialize only `c0..c95`. A zero count, truncated payload, or range crossing
`c95` is rejected.

The D3D8 assembler represents vertex `def` constants with these declaration
tokens; the D3D8 WDK marks the function-stream `D3DSIO_DEF` opcode as
pixel-only. The function parser therefore rejects that opcode instead of
inventing D3D9 constant precedence inside a D3D8 object.

## Function grammar and semantics

The function must begin with exactly `D3DVS_VERSION(1,1)`, end exactly once,
and contain at most 128 weighted instruction slots. NOP consumes one slot;
bounded COMMENT tokens consume none. Destination shift/saturate modifiers,
co-issue, pixel-only modifiers/opcodes, unknown token bits, and invalid
register numbers are rejected.

Register files are the D3D8 `vs_1_1` files: `r0..r11`, `v0..v15`,
`c0..c95`, `a0.x`, `oPos`, `oFog`, `oPts`, `oD0..oD1`, and `oT0..oT7`.
Sources may use general swizzles and the negate modifier. Scalar instructions
require a replicated source component. Only `MOV` may write `a0.x`.
The one-port `vs_1_1` input and constant files permit unlimited reads of one
`v#` and one `c#` address per ordinary instruction, not reads of multiple
distinct registers in either file. Matrix instructions reserve their constant
port for the consecutive matrix rows, so their vector source cannot also be a
constant. The parser enforces these rules even when called with hostile tokens.

| Family | D3D opcodes | Weighted slots | ARB strategy |
| --- | --- | ---: | --- |
| vector arithmetic | `mov add sub mad mul dp3 dp4 min max slt sge dst lit` | 1 | direct ARB operations; `lit` stages D3D's exact 8.8 exponent clamp |
| reciprocal | `rcp rsq` | 1 | scalar RCP; absolute scalar before RSQ where required |
| exponential | `exp expp` | 10 / 1 | full `EX2`; partial vector `EXP` |
| logarithm | `log logp` | 10 / 1 | absolute, zero-safe logarithm; partial precision may be exceeded |
| fraction | `frc` | 3 | `FRC`; `vs_1_1` permits only `.y` or `.xy` |
| matrix | `m4x4 m4x3 m3x4 m3x3 m3x2` | 4 / 3 / 4 / 3 / 2 | consecutive `DP4` or `DP3` rows |

Matrix instructions enforce their D3D destination masks and constant-source
restrictions. Every `oPos` write must use the full four-component mask, while
`oFog` and `oPts` accept only one component. Texture output writes accumulate.
Texture-output masks are prefix masks (`x`, `xy`, `xyz`, `xyzw`), and writing
`oTn` requires all preceding texture outputs to have been written.

At END, translated position is held in a temporary and emitted as:

```text
MOV result.position.x, qp.x;
MUL result.position.y, qp.y, program.local[0].x;
MAD result.position.z, qp.z, {2.0}, -qp.w;
MOV result.position.w, qp.w;
```

That is the required D3D `[0,w]` to GL `[-w,w]` depth conversion. Local
parameter zero supplies `+1` for presentation targets and `-1` for ordinary
render textures, matching the working fixed-function target-storage convention
before viewport and culling state are applied. This is target policy, not
game-specific shader rewriting.

`oFog` is D3D's final blend factor (`1` near/no fog, `0` fully fogged), while
OpenGL linear fog consumes a coordinate. The translator therefore emits
`result.fogcoord = 1 - oFog`; host linear fog state uses start `0`, end `1`.
The epilogue also computes D3D post-divide `z = qp.z / qp.w`. Local parameter
zero's `y` component selects that value whenever table fog is active, ensuring
table modes do not depend on OpenGL's implicit compatibility fog coordinate.

### User clip planes

Direct3D treats `SetClipPlane` equations as clip-space equations while a
programmable vertex shader is active. ARB vertex programs that write position
cannot use OpenGL's fixed user clip planes, so the ARB program alone is not a
complete execution path for the driver's six advertised planes.

The host integration must create a compatibility-GLSL vertex variant when a
programmable shader can be used with user clipping. It preserves the original
D3D `oPos` in `gl_ClipVertex`, emits the depth-converted value to
`gl_Position`, and defines the GL clip equations under identity model-view
state so their coefficients remain in D3D clip space. The existing scalable
HWTL GLSL bridge already proves that vertex-only GLSL can coexist with the
fixed and ARB fragment paths. Capability enablement requires exact tests for
all six planes, enable masks, `D3DRS_CLIPPING`, and clipped interpolation; a
no-clip ARB fast path may remain only if both variants are equivalent for
ordinary draws.

The capability-off translator deterministically converts the already
validated ARB instruction stream into that GLSL 1.10 variant rather than parsing
D3D bytecode a second time. It maps all 16 attributes to their D3D register
numbers, preserves the 96 constants plus relative-address sentinel, implements
the complete emitted ARB operation subset, and captures the original `qp` in
`gl_ClipVertex` before the target-orientation/depth epilogue mutates it. The
worst valid 128-slot relative-address program remains inside a bounded 128 KiB
source buffer. A real-host compile gate covers the comprehensive instruction
fixture. The transport-43 host integration now creates and owns a keyed GLSL
variant beside every ARB program, binds all 16 attributes before link, uploads
the 96 live constants and target/fog control, and selects the GLSL program only
while clipping and at least one user plane are enabled. It defines all six plane
equations under identity model-view state and restores the ARB fast path and
fixed/internal vertex paths without leaking clip enables. The exact host oracle
tests each of the six plane slots independently: the rejected half of a quad
must remain black while the retained half is red. The `.209` public capability
uses this path. Its signed real-XP probe proves plane zero with an exact clipped
frame, while the deterministic real-host oracle independently covers all six
plane slots.

## Relative constant addressing

`MOV a0.x, source` rounds to the nearest integer. ARB `ARL` floors, so the
logical D3D address is retained in a float temporary and generated with
`ADD 0.5` followed by `FLR`. A relative constant read is invalid before this
initialization.

D3D requires an out-of-range `c[a0.x + n]` read to return zero, while native
ARB relative array behavior is undefined. The translated parameter array adds
a private literal-zero sentinel at index 96. Each relative source therefore:

1. adds its constant offset to the logical address;
2. clamps a candidate address to `0..95`;
3. computes an in-range mask from the unclamped address;
4. selects the candidate when in range or sentinel index 96 otherwise; and
5. loads the selected array element through ARL.

The original swizzle and negate are then applied to the guarded temporary.
The sentinel avoids the `infinity * 0` and `NaN * 0` trap that a post-load mask
would have, and the computed absolute index also avoids ARB's smaller literal
relative-offset range.

The exact path needs the twelve D3D temporaries plus position, scalar-output,
logical-address, logarithm, and relative-source scratch temporaries. Host
temporary capacity is queried and enforced before the capability is exposed;
silently weakening the out-of-range rule to fit a minimum ARB implementation
is not acceptable.

## Transport and execution phases

Transport version 41 introduced the live shader object lifecycle. Transport
version 42 added the capability-off programmable draw packet. Transport version
43 adds the paired compatibility-GLSL user-clip program and raises only that
bounded source class to 128 KiB. The changes are:

- add ARB vertex type 1 and keyed GLSL clip type 3 to the existing shader
  define/delete IOCTLs;
- raise the bounded shader-source payload to 64 KiB; the adversarial valid
  128-slot expansion remains below 60 KiB after duplicate relative reads are
  folded to one guarded load per instruction;
- permit only the generated GLSL clip source class to use a 128 KiB bound;
- give guest programmable vertex programs a namespace distinct from pixel
  programs and internal fixed-function HWTL programs;
- append a compact programmable-vertex declaration and vertex payload at the
  existing `vertices[0]` byte offset only for programmable draws, leaving the
  common request header and every fixed/software-VP packet unchanged;
- carry 96 float4 constants and the bound vertex program in programmable
  draws; and
- bind generic vertex attributes on the host, execute the ARB vertex program
  or its user-clip GLSL peer, and preserve the current fixed/pixel pipeline
  downstream.

The implementation is deliberately checkpointed:

1. standalone declaration/function parser, translator, and deterministic
   contract tests with caps off;
2. guest object lifecycle, constants, declaration repack, and transport with
   caps off;
3. exact host GL acceptance for arithmetic, matrices, addressing, depth,
   colors, texture coordinates, fog, and point size;
4. signed real-XP acceptance through stock D3D8, including state blocks,
   reset, delete/recreate, invalid input, and teardown; then
5. advertise `vs_1_1` and 96 constants and rerun the full fixed-function,
   software-VP, OpenGL, D3D8, legacy-D3D9, and game regression matrix.

As of signed package `.215`, steps 1 through 4, the automated portion of step 5,
and a bounded representative-game regression pass are complete. The live XPDM
path consumes bounded DP2
operations 45 through 48, defines vertex ARB programs in a namespace separate
from pixel and internal HWTL programs, reloads declaration constants at each
bind, preserves the result through custom state-block capture/replay, and
deletes declarations and host programs during explicit deletion or
context/process teardown. Each vertex object also owns an idempotently deleted
GLSL clip variant; failed pair creation leaves no partial live object, and
miniport teardown deletes remaining host programs before releasing transport.

The declaration repacker preserves exact raw stride and SKIP bytes while
converting only little-endian `D3DCOLOR` BGRA storage into the RGBA bytes used by
a normalized generic attribute. Programmable draw packets carry
register-indexed formats, 96 constants, clip state, and bounded raw records.
Hostile or truncated packets fail closed. A shader read of undeclared v1-v15
uses the deterministic current generic attribute `(0,0,0,0)` after disabling
the array; only declared registers carry format/offset metadata. Missing v0
still fails closed because ARB vertex programs define no current generic
attribute zero. Nonindexed and indexed emitters preserve list/strip/fan
expansion and circular execute-buffer rules. The miniport validates namespaces
and texture-output routing, uploads all 96 constants, binds typed attributes in
Mesa's required alias order, and preserves fixed-function pixel, texture, fog,
blend, depth, cull, fill, point, and presentation state.
The standard bit-31 parameter marker is required on
every source and destination token, matching bytecode emitted by the stock
D3D8 runtime.

The focused `qxpd3dvsprobe.exe` workload uses only the stock System32 D3D8
runtime. It requires the public 1.1/96 caps, creates a hardware-VP fullscreen
device, declares `FLOAT3` position plus `D3DCOLOR`, executes `ADD oPos,v0,c0`
and `MOV oD0,v1`, uploads `c0.x = 0.4`, and renders through both the GLSL
user-clip path and the ARB no-clip path. `-D3dVs11` brackets those two scenes,
forces deterministic host readback, requires exact `0B1D2E/FF2080` and
`0B1D2E/20C060` samples, verifies define/delete and draw/present counters, and
requires clean teardown. The expanded signed `.211` pass also creates two
shaders with opposite declaration-defined `c0.x` values, proves custom
state-block Apply and Capture restore both the handle and declaration constant,
and draws after each replay. Its lifetime phase follows the valid public order:
apply a state block while its shader is live, unbind, delete the state block,
delete the shader, recreate a distinct shader, bind, verify, draw, and delete it.
State blocks do not extend the public lifetime of a deleted D3D8 shader handle.
A delete-then-Apply experiment was removed after stock XP hung inside `d3d8.dll`
without sending `DELETEVERTEXSHADER` or `STATESETEXECUTE` to the DDI.

The display driver records whether a state-block vertex value was a programmable
handle. Replay of a missing programmable object therefore fails closed instead
of reinterpreting the stale numeric value as an FVF. Explicit vertex and pixel
shader deletion unlinks the guest object before deleting host programs, so binds
arriving after the unlink cannot acquire a program during teardown. The focused
gate now requires six vertex/clip program definitions, six host vertex and clip
deletions, at least five explicit display-driver vertex deletes, six pre-Reset
draw/presents, one post-Reset draw/present, exact clipped and fast-path frames,
and clean teardown. The broad stock-D3D8 and legacy-D3D9 suites also pass,
including their general state-block and Reset gates.

Package `.212` pins the owning D3D context from table lookup through complete
DP2 dispatch. Destruction marks the context pending and rejects new dispatches;
an active slot cannot be zeroed or reused until its last dispatch releases the
pin. Palette, state-block, and HWTL detachment remains serialized under the
table lock, while host shader deletion and transport close run only after the
slot is detached. A platform-independent two-pin fixture proves deferred
destruction, acquisition refusal, final-release cleanup, idle destruction,
underflow behavior, and reference-overflow rejection.

Package `.213` scopes every programmable vertex and pixel shader table operation
to a complete device, process, and context owner tuple. Create, bind, state-block
record/capture/replay lookup, explicit delete, draw resolution, and context
teardown therefore cannot acquire an object merely because its runtime-local
handle and context number match another owner. A portable oracle proves exact
matching and rejects context-number reuse across a different process or device.

Harness checkpoint `b104047` adds a real stock-XP process-succession gate. Two
separate processes run the complete focused workload through System32 `d3d8.dll`;
the first exits before the second reuses the same runtime-local workload. The
gate requires both child results, four context/host opens, twelve shader and clip
definitions, complete host/clip deletion, the exact `6,1,6,1` Reset-session
pattern, fourteen draws/presents, exact second-child clip and fast-path pixels,
and clean teardown. This proves sequential teardown and reacquisition without
stale programs or transport refusal.

Harness checkpoint `1aa83cd` closes simultaneous stock-XP multi-context
isolation. One process creates two windowed hardware-VP devices, and the stock
runtime assigns both the same public shader handle `3`. Opposite constants and
four exact ordered frames prove A-to-B-to-A context switching. Device A is then
destroyed; its host program disappears while device B retains the numerically
identical public handle, constant state, and exact survivor frame. The gate
requires two contexts over one reference-counted transport, paired host/clip
definition and deletion, four draws/presents, no DP2 failure, and clean teardown.

Package `.214` makes the surrounding D3D context-create boundary transactional.
The display driver reserves a table slot before the blocking transport open and
initial render-target bind, but reserved slots are not findable by DP2 dispatch,
cannot be publicly destroyed, and cannot be reused. Only after both operations
succeed does the driver publish the public handle under the table lock. Every
pre-publication failure closes an opened transport, invalidates owner surface
upload generations that may refer to released host textures, releases state-block
and internal HWTL state, rolls the reservation back, and zeroes the slot. A
portable state-machine oracle models transport-open, target-upload, and
target-bind boundaries plus duplicate/corrupt transitions. The fresh signed T2
matrix then proves exact simultaneous and sequential shader owners, Reset, broad
D3D8, legacy D3D9, native OpenGL, and clean teardown with transport 43 unchanged.

Harness checkpoint `680ab15` adds a capture-free public-VS1.1 measurement that
uses only System32 `d3d8.dll`. Four fresh hardware-VP devices run in
fixed/shader/shader/fixed (ABBA) order. Each phase submits one warm-up frame and
sixteen measured frames with sixteen public `DrawPrimitiveUP` calls per frame;
the fixed control uses `XYZRHW`, while the programmable phase creates and binds
a public pass-through `vs_1_1` shader. The stock runtime coalesces the sixteen
API calls in each frame into one 48-vertex DP2 request. The exact host gate
therefore requires 272 API calls but only seventeen transport
draws/presents/batches per phase, plus four context/session lifecycles, two
vertex/clip program pairs, four ordered host profile blocks, and clean teardown.

Three repetitions of the current harness on signed `.214` measured median
values of 552 ns per fixed API draw, 564 ns per programmable API draw, 6.126 ms
for shader creation, 33.051 ms per fixed `Present`, and 23.876 ms per
programmable `Present`. These are CPU-visible guest timings on the registered
`.214` acceptance target, not GPU-complete timings or game FPS. They also expose
a measurement confounder: `.214` emits the large routine `D3D DRAW TRACE` packet
dump for the first sixteen fixed-function draws in each context, but not for
programmable draws. The Present difference is therefore not yet evidence that
the programmable renderer is faster. The next discriminating change is to put
routine draw/clear packet dumps behind the existing verbose-trace build switch,
retain concise lifecycle/failure markers and close counters, then rerun the same
paired fixture before selecting a rendering or transport optimization.

Signed `.215` makes those routine draw/clear packet dumps opt-in under
`QXP_VERBOSE_TRACE` while retaining the concise lifecycle, failure, counter,
and profile markers used by the acceptance gates. Three clean repetitions of
the identical ABBA fixture measured medians of 574 ns per fixed API draw,
585 ns per programmable API draw, 6.060 ms shader creation, 24.177 ms per fixed
`Present`, and 25.191 ms per programmable `Present`. All exact counters,
ordered profiles, shader lifetimes, and teardown gates passed without routine
packet traces. The large `.214` fixed/shader Present difference disappeared,
confirming that it was instrumentation contamination rather than evidence of a
rendering-path speed difference.

A direct capture-free Max Payne comparison used separate `.214` and `.215`

A capture-free Max Payne menu run measured 2,891 draws and 149 presents over
